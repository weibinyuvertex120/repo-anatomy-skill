# 陌生开源项目首次使用写作规范

## 适用范围

本规范用于撰写“第一次接触并实际使用一个陌生开源项目”的研究型教程、采用指南或内部上手手册。目标不是复述 README，也不是堆叠所有安装选项，而是帮助读者在证据充分、风险可控、结果可观察的前提下，完成一次最小但真实的成功使用，并判断是否值得继续投入。

适用于以下对象：

- 命令行工具、库、框架、服务、插件、Agent 工具、MCP Server、编辑器扩展和开发基础设施。
- 需要本地安装、容器运行、源码构建、包管理器安装或远程服务接入的项目。
- 需要写入 Agent 客户端上下文文件、配置权限、调用外部工具或访问工作区的项目。
- 需要从“能启动”进一步验证到“能完成一项真实工作”的首次采用场景。

不适用于只做新闻概述、版本发布摘要、纯 API 字典或已经稳定运行后的深度运维手册；这些文档可引用本规范中的证据、风险和验证方法，但不应强行套用完整首次使用路径。

## 核心原则

写作必须围绕一个可审计的采用链路展开：

```text
项目身份与用途
-> 项目状态与治理
-> 许可证与安全
-> 环境前置条件
-> 安装来源与版本
-> 最短成功路径
-> 可观察验证
-> Agent 上下文与权限
-> 真实工作流
-> 求助、升级、回滚与维护
-> 停止条件
```

该顺序同时是研究顺序和风险闸门。前一阶段存在阻断性未知时，不应把后一阶段写成已经可执行的事实。可以并行收集证据，但最终文档必须让读者按照上述顺序作出决定。

始终遵守以下原则：

- 研究按证据位置展开，成文按读者行动顺序组织。
- 先确定成功结果，再选择安装和配置路径。
- 优先提供一条最可能成功的主路径，其他路径放在主路径之后并说明适用条件。
- 每个关键操作都必须有可观察结果；“没有报错”不能替代更强验证。
- 明确区分文档声明、实际执行结果、合理推断、编辑建议和未知项。
- 不把流行度、徽章、提交频率或安全评分直接等同于质量、安全或可维护性。
- 不把 Agent 的上下文指令文件当成权限控制、沙箱、认证或审批机制。
- 不因完成最小演示就推断项目已适合生产环境。

## 研究简报

开始检索前，先记录以下内容：

- **目标读者：** 开发者、运维人员、数据分析人员、内容工作者或 Agent 用户；其现有知识与可接受的命令行复杂度。
- **采用目标：** 读者最终要完成什么任务，而不是仅仅“安装项目”。
- **目标环境：** 操作系统、CPU 架构、Shell、容器环境、运行时、包管理器、编辑器或 Agent 客户端。
- **风险级别：** 是否接触生产数据、凭证、个人信息、外部网络、系统级权限或不可逆操作。
- **验证能力：** 研究环境是否允许真实安装、执行、联网、创建临时文件、启动服务和调用外部 API。
- **版本基线：** 计划验证的项目版本、提交或发布通道，以及研究日期。
- **输出模式：** 面向初学者的教程、团队采用指南、Agent 操作手册或决策型项目分析。
- **停止边界：** 哪些未知或失败会阻止继续推荐，哪些只需要作为限制披露。

## 必答研究问题

### 1. 项目身份与用途

- 项目的官方名称、官方仓库、维护主体和主要发布渠道是什么？
- 它解决的具体问题是什么？输入、处理和输出分别是什么？
- 它是独立应用、库、框架、插件、协议实现、资源集合还是托管服务客户端？
- 官方描述与实际能力之间是否存在范围差异？
- 哪类用户和工作流能直接获益？哪些场景不需要它或不应使用它？
- 一次“首次成功使用”的最小可观察结果是什么？
- 项目名称是否存在同名包、仿冒仓库、迁移仓库或已废弃前身？

### 2. 项目状态与治理

- 仓库是否活跃、只读、归档、迁移、分叉或处于维护模式？
- 默认分支、最新稳定版本、预发布版本和最近关键提交分别是什么，核验日期是什么？
- 谁拥有发布权限，维护者和组织归属是否清晰？
- 是否有贡献指南、行为准则、治理说明、路线图和发布策略？
- Issue、讨论区和安全报告渠道是否可用？维护者如何处理缺陷和破坏性变更？
- 是否有自动化测试、持续集成、版本标签、变更日志和可复现发布证据？
- 活跃度下降是成熟稳定、维护资源不足还是项目停止的信号？证据能否区分？
- 依赖生态、关键维护者集中度和组织持续性会带来什么维护风险？

不要用 star、fork、下载量或提交数量替代治理判断。所有易变指标必须附精确核验日期，且只作为背景信号。

### 3. 许可证与安全

- 根目录许可证是什么，具体版本、例外条款和适用范围是什么？
- 仓库中的示例、文档、模型、字体、数据集、二进制文件和第三方组件是否采用不同许可证？
- 许可证是否允许目标场景中的商用、修改、分发、SaaS、静态链接或专利使用？
- 是否有 NOTICE、版权声明、贡献者许可协议或商标限制？
- 是否存在 SECURITY 文件、安全公告、漏洞披露流程和受支持版本列表？
- 安装脚本、容器镜像、二进制发行物和包注册表条目来自谁，能否验证完整性或签名？
- 运行时需要哪些文件、网络、系统、容器、浏览器、云账户或组织权限？
- 项目会读取、上传、记录或缓存哪些数据？默认遥测、崩溃报告和第三方服务是什么？
- 已知漏洞、供应链风险、依赖风险和未修复安全问题是否影响最短路径？
- 哪些安全结论是官方自述，哪些经过复现、扫描或独立审计？

许可证判断应基于实际许可文本和目标用法，不能把“开源”“免费”或公共仓库等同于任意商业使用许可。对高风险或有法律后果的场景，文档只能给出风险提示与待确认项，不替代法律意见。

OpenSSF Scorecard 或类似自动化评分只能作为风险信号：它可以提示分支保护、依赖更新、令牌权限、发布实践等需要检查的区域，但不能单独证明项目安全，也不能因低分就断言项目恶意或不可用。必须回到具体检查项、证据日期、项目架构和实际威胁模型解释结果。

### 4. 环境前置条件

- 支持哪些操作系统、CPU 架构、运行时、浏览器、数据库和容器版本？
- 需要哪些编译器、系统库、包管理器、构建工具、后台服务或账户？
- 是否要求 Git、SSH、Docker、GPU、特定 Shell 或管理员权限？
- 最低版本与推荐版本是否不同？官方文档、CI 配置和实际依赖声明是否一致？
- 端口、磁盘、内存、网络代理、证书和区域限制是什么？
- 是否需要 API Key、OAuth、云凭证、许可证密钥或组织管理员批准？
- 哪些前置条件可以用命令或界面状态预检？预期结果是什么？
- Windows、macOS、Linux、WSL、容器和远程开发环境有哪些差异？

前置条件必须在安装命令之前出现。对于每项硬性条件，给出最小预检方法；不能确认时明确标注“未验证”，不要生成看似合理的命令。

### 5. 安装来源与版本

- 官方推荐安装来源是什么：发布页、官方包注册表、官方镜像、插件市场还是源码？
- 包名、组织名、镜像名和发布者身份能否与官方仓库交叉验证？
- 文档中的“latest”当前指向什么版本，稳定版和预发布版如何区分？
- 是否需要锁定版本、校验哈希、验证签名或生成依赖锁文件？
- 安装命令是否适用于目标平台、Shell、工作目录和权限级别？
- 全局安装、本地安装、容器安装和源码构建各自改变哪些系统状态？
- 升级或卸载是否会保留配置、数据、缓存和凭证？
- 是否存在已知恶意同名包、社区维护包或与官方不同步的镜像？

主路径优先选择官方维护、版本可锁定、修改范围最小且容易回滚的来源。源码构建、夜间版本、第三方包和手工复制应作为有明确理由的替代路径，不与主路径并列呈现。

### 6. 最短成功路径

最短成功路径不是最短命令数，而是从干净、已满足前置条件的环境到首个可验证结果之间，风险最低且解释充分的路径。必须包含：

1. 操作目标。
2. 起始环境和工作目录。
3. 需要创建或修改的文件。
4. 精确版本的安装或启动命令。
5. 最小配置，包括配置放置位置。
6. 一个安全、可重复、低成本的示例输入。
7. 预期输出或状态。
8. 清理或回滚方式。

每个关键步骤采用以下操作单元：

```text
操作目标
-> 操作入口或命令
-> 必要输入与作用范围
-> 可复制示例
-> 可观察验证
-> 常见失败与最小纠正
```

禁止在主路径中同时铺开所有包管理器、容器、源码构建和高级配置。若官方存在多个“一键安装”入口，应根据目标读者、环境和可验证性选择一个，并说明其他入口何时更合适。

### 7. 可观察验证

验证至少覆盖三层：

- **存在性：** 可执行文件、包、插件、服务、配置或工具条目确实存在。
- **功能性：** 使用受控输入执行核心能力，并得到明确输出。
- **边界性：** 至少验证一个重要限制、拒绝行为、权限边界或失败模式。

可接受的观察点包括：

- 版本命令返回准确版本和构建信息。
- 状态命令显示服务就绪、连接成功或配置已加载。
- Agent 的工具列表中出现目标工具，并能完成受控只读调用。
- 生成的文件、结构化字段、日志事件或数据库记录符合预期。
- 受限目录、危险命令或未授权网络访问按预期被拒绝。
- 进程、端口、容器健康检查或测试用例进入预期状态。

对每个验证说明：执行环境、命令或入口、输入、预期结果、实际结果、验证日期和版本范围。仅阅读文档时，不得写成“已运行成功”；应写明“根据官方文档可执行，未在本环境复现”。

### 8. Agent 上下文与权限

当项目通过编程 Agent、编辑器 Agent 或通用智能体使用时，必须分别研究“Agent 如何获得上下文”和“Agent 实际拥有什么权限”。两者不能混写。

上下文文件通常用于告诉 Agent：

- 项目目标、目录结构和术语。
- 构建、测试、格式化和验证命令。
- 代码风格、架构约束和禁止修改区域。
- 首选工具、证据保留方式和交付格式。
- 针对目录、文件类型或任务的补充规则。

上下文文件不等于权限边界。它通常不能替代：

- 操作系统文件权限和用户身份。
- 沙箱、容器隔离和工作区范围。
- 工具允许列表、命令审批和网络访问策略。
- API 认证、密钥管理、OAuth 授权和云端 IAM。
- 分支保护、代码评审、CI 门禁和部署审批。
- 数据分类、审计日志、速率限制和人工确认。

写作时必须明确说明：上下文指令可能约束 Agent 的行为倾向，但恶意输入、提示注入、客户端缺陷、工具配置或用户授权仍可能让实际能力超出文字约束。安全边界必须在客户端设置、工具层、操作系统、网络和服务端权限中落实，并用实际拒绝测试验证。

#### Agent 客户端指令文件差异

下表用于研究和写作定位，不应代替目标客户端当前版本的官方文档。文件名相似不代表发现顺序、继承规则、作用域或语法相同。

| 客户端 | 常见项目指令入口 | 作用域与组织方式 | 写作时必须核验 |
|---|---|---|---|
| Claude Code | `CLAUDE.md`、`.claude/rules/` | `CLAUDE.md` 用于项目或目录上下文；`.claude/rules/` 可拆分主题规则，并可能按路径或规则元数据限定作用范围 | 查找层级、导入机制、个人与团队配置、规则匹配方式、当前版本是否支持所写语法 |
| Codex | `AGENTS.md` | 常按目录层级发现；更深目录中的文件用于更具体的子树约束 | 搜索根、继承和覆盖顺序、适用目录、与用户/系统指令的优先级、实际执行审批配置 |
| Gemini CLI | `GEMINI.md` | 可在用户级和项目目录中提供上下文；可能支持分层发现或导入 | 文件发现范围、层级合并、导入语法、客户端设置中的上下文文件名与批准模式 |
| GitHub Copilot | `.github/copilot-instructions.md`、`.github/instructions/*.instructions.md` | 前者通常提供仓库级指令；后者可按文件或路径拆分指令 | 支持的产品表面、路径匹配元数据、是否自动应用、组织级策略与仓库指令的关系 |
| Cursor | `.cursor/rules/*.mdc`（Cursor Rules） | 规则文件可按描述、文件模式或应用方式组织；旧项目可能仍出现遗留规则文件 | 当前推荐格式、规则类型、glob 匹配、自动附加条件、遗留格式迁移和实际 Agent 模式 |

写客户端配置示例时：

1. 先注明客户端名称、版本或核验日期。
2. 只使用该客户端正式支持的路径和语法，不把其他客户端的约定直接改名复用。
3. 说明文件放置位置、适用目录和是否提交到版本库。
4. 给出最小规则，避免在首次路径中塞入长篇项目百科。
5. 设计一个可观察测试，确认规则是否被加载，例如要求 Agent 复述指定约束、执行规定测试或拒绝修改受保护路径。
6. 另行检查实际工具权限、命令审批、网络能力和秘密访问；不能用“已写入规则”代替权限验证。
7. 将客户端指令视为项目文档的一部分，安排评审、版本控制和定期更新。

Agent 提示或任务说明至少应包含：

- 任务目标和允许修改的范围。
- 应优先使用的工具或项目命令。
- 必须保留的证据、日志或引用。
- 禁止动作与需要人工确认的动作。
- 预期输出、验证方法和停止条件。

不要只写“请使用该工具完成任务”。对于会写文件、执行命令、访问网络或使用凭证的 Agent，示例必须从只读或可回滚操作开始。

### 9. 真实工作流

完成最小演示后，增加一个与读者目标一致的真实工作流。它应比 Hello World 更接近实际采用，但仍保持可控和可回滚。

真实工作流必须说明：

- 工作从哪里开始，输入来自什么系统或文件。
- 项目在整个流程中承担哪一步，不承担哪一步。
- 上游和下游工具、格式、接口及责任人是什么。
- 数据是否离开本机，是否包含秘密、个人信息或受限内容。
- 如何记录版本、配置、命令、输出和人工决策。
- 成功标准、性能基线和失败后恢复方式。
- 哪些步骤可以自动化，哪些步骤必须保留人工复核。
- 如何把一次性试验转成可重复脚本、锁定配置或团队文档。

真实工作流不能只重复安装示例。至少验证一个集成点或交付物，并说明该结果对采用决策意味着什么。

### 10. 求助、升级、回滚与维护

#### 求助路径

- 官方文档、FAQ、故障排查页和搜索入口。
- Issue、Discussions、社区频道或商业支持的适用边界。
- 提问前需要收集的版本、平台、日志、最小复现和脱敏信息。
- 安全问题应走的私密披露渠道，不能默认公开 Issue。

#### 升级策略

- 稳定版、长期支持版、预发布版和主分支之间的选择。
- 破坏性变更、迁移指南、弃用周期和兼容矩阵。
- 升级前备份、锁文件、测试环境和回归检查。
- 升级后版本、核心功能、权限和真实工作流的重新验证。

#### 回滚策略

- 如何恢复上一版本、旧配置、数据备份或容器镜像。
- 哪些迁移不可逆，是否需要先导出数据或快照。
- 全局安装、后台服务、Shell 配置和凭证残留如何清理。
- 回滚验证的可观察结果是什么。

#### 维护策略

- 谁负责跟踪发布、安全公告和依赖更新。
- 多久复核版本、许可证、客户端指令和权限配置。
- 如何保存版本基线、部署记录和已知限制。
- 项目停更、维护者变化或关键依赖失效时的替代方案。

## 来源优先级

针对每项声明，选择最接近实现、最符合当前版本且可追溯的来源。推荐优先级如下：

1. **官方发布与规范：** 官方仓库、许可证原文、发布页、软件包注册表中的官方发布者、正式文档、安全公告、支持矩阵和迁移指南。
2. **官方实现证据：** 源代码、依赖清单、构建脚本、CI 配置、测试、示例、Schema、容器定义、默认配置和维护者 Issue/讨论。
3. **上游权威来源：** 标准组织、运行时或平台官方文档、原始研究论文、操作系统与云平台安全文档。
4. **可信独立证据：** 方法透明的技术分析、独立审计、可复现实验和明确标注版本的专业报告。
5. **社区经验：** 论坛、博客、问答、社交媒体和聚合站，仅用于发现故障模式、用户体验或待核实线索。

补充规则：

- README 是入口，不是所有事实的最终权威。版本、安装和兼容性应与发布页、包注册表、代码和 CI 交叉验证。
- 项目自己的性能、安全和易用性声明属于“来源声明”，除非有独立或实际复现证据。
- 搜索摘要、AI 生成摘要和二次转载不能作为关键操作的唯一证据。
- 来源冲突时，先检查日期、版本和适用平台；优先采用最接近当前实现的来源，并披露会改变用户行动的冲突。
- 找不到证据时记录未知，不用惯例、记忆或相似项目补齐。

## 事实账本

研究期间维护事实账本。它是写作和审校的工作材料，不必原样出现在最终文档，但关键结论必须可回溯。建议字段如下：

| 字段 | 要求 |
|---|---|
| `claim_id` | 唯一编号，便于正文、证据和复核记录关联 |
| `claim` | 单一、可验证的原子声明，避免一行混合多个事实 |
| `research_question` | 对应的研究问题或章节 |
| `claim_class` | 已验证事实、来源声明、推断、建议或未知 |
| `decision_impact` | 阻断、重要、一般或背景；说明会影响什么决定 |
| `source_title` | 来源标题或仓库文件名 |
| `source_owner` | 官方组织、维护者、标准机构、独立研究者或社区 |
| `source_type` | 文档、发布、代码、测试、Issue、安全公告、审计或实际执行 |
| `source_location` | 精确 URL、仓库路径、标签、提交或文档锚点 |
| `source_date` | 来源发布日期或最后更新时间，未知时明确记录 |
| `verified_date` | 研究者实际核验日期，使用绝对日期 |
| `version_scope` | 适用版本、提交、平台、客户端和配置范围 |
| `evidence_excerpt` | 支持声明的短摘录、字段或代码位置；避免大段复制 |
| `verification_method` | 文档交叉验证、源码检查、命令执行、界面检查或受控测试 |
| `actual_result` | 实际观察结果；未执行时写明原因，不虚构成功 |
| `confidence` | 高、中、低，并说明降低置信度的因素 |
| `caveat` | 平台差异、条件、冲突、未知或例外 |
| `next_check` | 发布前、采用前或升级后需要再次核验的事项 |

账本维护规则：

- 动态事实必须记录 `verified_date` 和 `version_scope`。
- 安装命令、权限要求、数据流、安全结论和许可证范围应拆成独立声明。
- 推断必须列出支撑事实，不能伪装成项目官方结论。
- 实际执行与文档审查使用不同的 `verification_method`。
- 失败结果同样进入账本，包括错误信息、环境和已排除原因。
- 关键声明只有低置信度时，正文必须披露或停止给出确定性建议。

## 写作模板

最终文档可使用以下结构，并根据项目类型压缩非关键章节，但不能删除会影响采用决定的风险闸门。

### 结论与成功结果

- 一句话说明项目是什么、适合解决什么问题。
- 明确目标读者与不适用场景。
- 描述首次成功后的可观察结果。
- 给出“建议试用、条件试用、暂缓采用或不建议采用”的初步结论及关键原因。

### 当前项目状态

- 官方身份、维护主体、仓库和发布渠道。
- 当前稳定版本、核验日期、治理与维护状态。
- 已知限制、活跃度信号和仍未确认的风险。

### 采用前风险检查

- 许可证、第三方资产与目标用法。
- 安全报告、数据流、外部依赖与所需权限。
- Scorecard 等自动化信号的具体含义和局限。

### 前置条件与预检

- 目标平台、运行时、工具、账户、网络和资源。
- 每项硬性条件的检查方法和预期结果。

### 安装主路径

- 官方来源、锁定版本和完整执行上下文。
- 安装造成的系统变化。
- 可观察的安装验证和清理方式。

### 第一次成功使用

- 最小配置、受控输入、核心操作和预期输出。
- 存在性、功能性与边界性验证。
- 实际执行状态以及未复现部分。

### Agent 配置与权限

- 对应客户端的上下文文件、路径、作用域和最小示例。
- 规则加载验证。
- 独立列出工具权限、命令审批、网络、凭证和工作区边界。

### 真实工作流

- 一个端到端任务、集成点、交付物和验收标准。
- 自动化边界、人工复核、日志证据和失败恢复。

### 故障排查与维护

- 按症状组织常见问题：可能原因、检查点、最小修复和预期结果。
- 求助信息、升级步骤、回滚路径和维护责任。

### 采用决定与停止条件

- 哪些证据支持继续试用或扩大使用。
- 哪些未知必须由维护者、法务、安全或平台管理员确认。
- 何时停止、降级或切换替代方案。

## 停止条件

### 研究可以结束的条件

满足以下条件后可以停止继续扩展资料：

- 所有决策关键问题已有支持证据或显式未知。
- 项目身份、版本、许可证和官方安装来源已经交叉验证。
- 最短成功路径、可观察验证和清理方式已经明确。
- Agent 上下文文件与实际权限边界已经分别说明并验证到可行范围。
- 至少一个真实工作流及其风险、失败恢复和验收标准已经覆盖。
- 升级、回滚、维护和求助路径已经说明。
- 新增来源只重复已有证据，不再改变行动、风险或结论。

### 必须停止采用或执行的条件

出现以下情况时，不得继续写成可直接采用的主路径；应停止执行、降级为受限研究，或建议转交相关负责人：

- 无法确认官方仓库、包发布者、镜像来源或下载完整性。
- 许可证缺失、冲突或明显不允许目标用法。
- 安装要求来源不明的管理员脚本、关闭安全控制或暴露长期凭证，且没有可信替代路径。
- 最小操作会触及生产数据、外部付费服务、不可逆迁移或高权限系统，但没有隔离环境和明确授权。
- 项目需要的权限超出任务必要范围，且无法收窄或验证。
- 上下文指令声称限制行为，但客户端或工具层没有实际权限控制，风险不可接受。
- 关键安全公告、已知漏洞或不受支持版本直接影响当前路径，且没有修复版本或缓解措施。
- 文档、发布、代码和实际行为之间存在会改变安全或数据处理结论的重大冲突。
- 无法定义或观察成功结果，无法区分“运行了”与“正确工作”。
- 失败后没有可行的备份、清理或回滚路径。
- 研究环境不允许执行关键验证，而用户要求的是已验证可用性结论。

停止不等于项目永久不可用。必须记录停止原因、证据、影响范围，以及重新开始研究所需的明确条件。

## 失败模式

拒绝或返工存在以下问题的草稿：

- 按 README 标题顺序改写，没有形成采用决策链路。
- 开头罗列功能，却没有说明目标问题和成功结果。
- 把 GitHub star、下载量、最近提交或 Scorecard 分数当成安全与质量结论。
- 把公共仓库、“免费”或 OSI 名称直接写成目标用法已获许可。
- 给出安装命令，却没有官方来源、版本、工作目录、权限和预期结果。
- 同时列出多个安装方式而不选择主路径。
- 用“安装成功”“已连接”或“没有报错”代替可观察验证。
- 把文档中的示例写成已经在本地或目标平台实际执行。
- 只验证 Hello World，没有真实工作流、集成点或边界测试。
- 给 Agent 写了指令文件，就宣称文件系统、网络、凭证或命令权限已经受控。
- 混用 `CLAUDE.md`、`AGENTS.md`、`GEMINI.md`、Copilot 指令和 Cursor Rules 的语法或作用域。
- 未注明客户端版本或核验日期，却声称当前发现与继承行为固定不变。
- 遗漏许可证、安全、隐私、升级、回滚、维护或停止条件。
- 将证据缺口补成合理猜测，或隐藏相互冲突的来源。
- 给出生产采用建议，却没有说明验证范围和剩余未知。

## 交付前检查

- 文档严格覆盖从项目身份到停止条件的完整链路。
- 动态事实带精确核验日期和版本范围。
- 安装来源、包名、发布者和官方仓库已经交叉验证。
- 命令包含平台、Shell、工作目录、前置条件和预期结果。
- 最短成功路径只有一个明确主路径。
- 验证同时覆盖存在性、功能性和至少一个关键边界。
- 实际执行、文档声明、推断、建议和未知清楚区分。
- Agent 客户端文件路径、作用域和语法来自对应客户端当前文档。
- 上下文指令与实际权限控制分别成节，不存在等同表述。
- Scorecard 等评分只作为具体风险检查的线索。
- 真实工作流包含输入、输出、集成、验收、证据和恢复方式。
- 求助、升级、回滚、清理和长期维护责任明确。
- 阻断性风险触发停止条件，而不是被埋在脚注中。
- 没有未完成标记、模板残留、未经证实的“最新”、虚构输出或无法追溯的关键结论。
